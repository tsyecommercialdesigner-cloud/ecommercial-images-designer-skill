# 设计档案与确认记录

启动或恢复任务时阅读。本记录是设计交付和恢复上下文，不替代源码仓库的任务系统。可以在对话中维护 Markdown；涉及多个版本或多张图片时建议在用户工作目录落盘。不得将真实客户资料写入技能包、评测 fixtures 或公共仓库。

## 恢复不完整档案

先读指定档案及本节，再读本轮涉及的阶段资源。对于只改文字方案、没有待恢复服务任务的请求，档案能确定修改图号、反馈和保留范围就进入草案，不开展仓库勘察或团队状态发现。只读取档案明确引用且本轮确实需要的文件；缺少旧字段就记录缺口，不猜 README 等文件来寻找答案，不把目录或图片交给 UTF-8 文本读取工具。工作目录明确后无需反复查询。

分别恢复“字段值”和“确认依据／作用域”。旧版本存在、要求沿用原样或某张图已接受，都不能证明其他图或共享风格已确认。没有确认记录的状态写为 `unknown`，不能补写成已确认、已批准，也不据此断言用户过去从未确认。

原文案、尺寸、底图或风格值缺失时，保留缺口并继续有依据的局部布局草案；新增内容标为本轮建议，执行前再补齐值与确认依据。例如仅记载 M01 accepted 时，锁定 M01；M02 的背景和批准状态都缺失，应写“拟沿用旧风格，具体值与确认依据待核”，不能写“沿用原 M02 已批准的风格”。“保留原样”是修改范围约束，不是批准证据。恢复摘要、提示词与确认台账使用同一状态，不在提示词中暗自升级。

恢复时将“档案原值”“用户反馈”“本轮建议”分栏。原值未保存就写 `unknown`，包括旧边距、字号、文字层数、商品视角与位置；不能从“太挤”等反馈反推数值或补写旧稿，也不能在对照表、原因说明或提示词中悄悄填回。工具计算的图片摘要注明工具来源，不称为用户提供或用户确认。

### 纯文字恢复的专用交付

使用入口已直接索引的单图状态契约 revision 分支。它取代旧的四段散文、重复提示词和自由问题清单：state 仅复制原字段，proposal 仅定义局部新目标，next 仅列可修改范围的缺口与确认。

- state.locked_images 取本轮明确保留的已接受图；state.edit_images 仅含本轮修改图，next.confirm_images 与它相同。历史确认原话未存档不使本轮用户已给出的冻结指令变成 unknown。
- baseline 的原文、尺寸、数量、视角、风格等未记为 null；图片来源逐图取证，事实来源不填成图片来源。
- proposal.copy 逐字段等于 baseline；缺辅助文案时为 null。布局辅助元素 if_present=true，overflow=reflow_preserve_all_copy：行数约束不能删除或隐去已存在的原文。
- proposal.canvas 沿用 baseline.canvas，appearance 三项 null，不借局部排版新拟共享规范。位置与行数是新目标，不能伪装成历史值。
- next.rollback_stage=S2、stage=S3：最早回 S2 修改布局，再以新方案进入 S3；待补字段仅从 baseline 的 null 项取得。锁定图不进入确认范围，也不成为待补字段。

只交付这一份 JSON，未知旧稿不做成因推断或另给对照表。真正执行前补齐资料、核对当前版本并取得方案确认及执行授权；结构校验不替代这些授权。
## 任务头

记录 `design_id`、产品／型号、当前阶段 S0–S5、当前版本、任务类型（首次／修改／仅策划／文生图素材）、用户目标、受众、平台、图种与数量、尺寸／比例、品牌规范、产物目录、待定项，以及已有授权的范围。ID 用任务内稳定标识，不含客户秘密。

首次生成记录 `first_generation_images` 与用户提供它们的消息位置；若为空，记录用户明确要求文生图素材的原话。不得自行把无图片输入改写为“用户选择文生图”。修改任务关联原设计、原版本与底图；底图不存在时先恢复或请用户补充。

## 图片台账

| 字段 | 填写规则 |
|---|---|
| `image_id` | 如 P01、R01、G01；命名仅便于引用，不代替身份确认。 |
| `source` | 用户附件、已获准的本地绝对路径或可访问图片 URL；带鉴权的 URL 不进入共享文档。 |
| `identity` | product / reference / generated / unknown。 |
| `provenance` | 用户说明或可核对来源中的实拍／合成夹具／概念示意／unknown；与 product 等业务角色分开，不因用作商品依据就改称真实商品。 |
| `reference_use` | none / style / structure / both / unknown；reference 必须澄清为 style、structure 或 both。 |
| `product_variant` | 对应哪个商品／SKU；非当前产品时写明。 |
| `user_evidence` | 用户关于身份和参考用途的原话或消息位置。 |
| `observations` | 实际看见的外形、配色、标识、画面层级及可见限制；没看见的部分不猜。 |
| `observation_source` | 本轮看图的工具与图片身份，或明确标注所复用的历史观察来源；只读元数据时不填写视觉结论。 |
| `use_and_exclusions` | 哪些保留、借鉴、禁止带入；绘图请求用途明确为 upload / analysis_only / undecided。本轮免费看图的图片输入不等于未来绘图的上传清单。 |
| `generation_input_index` | 仅在确定实际绘图入口和上传清单后填写其序号；analysis_only 无上传序号，undecided 不猜序号。 |
| `content_identity` | 工具能提供时保存 SHA256／附件身份，防止同路径图片替换后误用旧确认。 |

一张图可以同时是产品依据和风格来源，但必须说明两种用途。参考图里的品牌、图形、文案或证明材料不能自动进入自己的商品方案。

## 事实与卖点

| 事实 ID | 当前产品的陈述 | 来源位置 | 类型 | 状态 | 允许的文案／限制 |
|---|---|---|---|---|---|
| F01 | 按实际资料填写 | 说明书页码／用户消息／实图 ID | 用户确认／规格资料／视觉观察 | confirmed / unknown / conflict | 仅对本型号、可见外形或带条件的表述 |

`confirmed` 表示能追溯到本次任务可用依据，不表示独立实验验证。保留“用户陈述”和“有检测资料支持”的区别。冲突不能靠覆盖旧值解决；记录双方来源、需要澄清的问题及影响的图号。若可删掉不确定主张并继续，向用户展示删改后的方案。

| 卖点 ID | 特征与事实 ID | 用户问题／收益 | 证据如何呈现 | 优先级与主题 | 待确认推论 |
|---|---|---|---|---|---|
| B01 | F01 等 | 具体场景中的价值 | 实拍／局部放大／已核实参数 | 主卖点或辅助信息 | 没有依据的效果不写成已证实 |

## 逐图方案与提示词

| 图号 | 用途／主题 | 主标题 | 副标题／标签／脚注 | 事实和卖点 ID | 产品图／参考图映射 | 画面和排版 | 完整提示词 ID |
|---|---|---|---|---|---|---|---|
| M01 / D01 / K01 | 一图的核心任务 | 逐字定稿或明确无文字 | 不自动增添促销／认证 | 引用已有条目 | 各图身份和参考用途 | 主体、位置、配色、字体、信息层级、留白 | 当前版本逐图保存 |

共享视觉规范另记主色／辅助色、字体许可状态和字重层级、产品尺度、光影、背景、图标与标注风格、文案语气。画面尺寸、长宽比和预期文件类型按图记录；模型不能保证精确尺寸时，在确认前说明计划如何验收或适配，不能静默裁掉商品。

## 版本、确认与失效

每版保存一份不可覆盖的方案快照。档案内的 `revision` 是本技能版本号；MCP 若另有版本／摘要，分别记录，不能假设两者相等。

| 字段 | 内容 |
|---|---|
| `revision` / `previous_revision` | 当前和前一版；附变更原因。 |
| `confirmed_scope` | 用户确认的图号、文案、排版、提示词、输入图映射及模型／尺寸／数量。 |
| `confirmation_evidence` | 用户原话与消息位置；未确认时为空，不允许 Agent 自填同意。 |
| `execution_authorization` | 是否要求提交、本次使用的服务、收费授权或已覆盖的预算／范围及依据。 |
| `invalidated_scope` | 新资料、图片内容、文案、布局、提示词或生成参数修改后，哪些确认已失效。 |
| `server_snapshot` | 保留历史服务 design_id／revision／digest 以便追溯；当前新任务只保存核心请求与实际任务身份，不依赖服务端策划。 |
| `server_panel_map` | 用户图号与本轮冻结 task_id／幂等键的映射；旧 panel_id 原样保留用于追溯。新 Nano 核心任务示例 M01→v3-M01，GPT 各图分别绑定提交键与返回ID。 |
| `approval_scope` / `submission_scope` | Skill中用户实际批准哪些图、此次执行哪些图；提交集合必须属于用户批准和费用授权覆盖的集合。 |

可先确认部分图并只为这些图构造核心生成任务，逐图保存确认和费用授权。未确认图不得混入提交；批量接口的图数上限只影响分批，不改变用户批准范围。

一个确认只对展示过的内容有效。新版本保留未受影响的约束与产物，但不能冒用旧服务 revision/digest 提交新方案。共享 style 的变更使其所有关联图的视觉确认受影响；如果用户要求保留旧图，记录保留它们属于旧视觉组，不声称新旧混合是一套已经验证一致的新版本。

每次改稿保留产品事实、来源、全部定稿文案和排版、完整提示词及图片映射，仅更新被点名图。共享规范改动列出关联图和新增确认范围，冻结旧图保留旧组；不依赖服务端 brief／suite／reference_replica 重建方案。旧 Server 档案原样保留，任务未知时先按原核心任务身份查询，不换键重提。

## 任务与验收台账

| 设计版本／图号 | MCP、实际工具、模型 | 原任务身份／幂等键 | 提交与当前状态 | 实际产物 | 视觉检查 | 用户验收 |
|---|---|---|---|---|---|---|
| 对应已确认版本 | 记录实际值 | task_id 及服务要求的 namespace/checkpointer/thread_id 等 | 时间、结果、错误和下载状态 | 文件路径／图片链接、实际尺寸、摘要（若有） | 检查项、问题、未能查看的限制 | pending / accepted / changes_requested / partial |

完整提示词、传入图片顺序和非秘密生成参数随快照保存；秘密只由 MCP 配置管理。生成完成而未看图、部分下载、用户尚未验收均单独记状态，不统一写“完成”。

提交前先保存 `prepared/submitting` 记录及幂等身份，响应后追加服务 task_id；不等收到响应才第一次记录请求。文件路径可变时记录本次实际字节摘要／冻结副本身份，不能用同路径替换后的新图沿用旧确认。已有任务正在运行或未知时，新反馈先记录为下一版计划；只在相关旧任务状态和授权已核清后执行，避免跨版本重复收费。

反馈记录包括用户原话、图号、观察到的问题、原因判断、回退阶段、影响范围和下一版差异。跨会话恢复时先查询未终结任务，不能因档案里暂时没有图片就重新提交。
