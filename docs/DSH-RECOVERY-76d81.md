## 诊断依据

前序最终批次为 `E:/dsh-skill-host-76d8-361b8b7755ea40a297ced966d9704088`。读取其 Sonnet recovery 的完整原生 events、实际 system/user 上下文、工具参数及最终答案，结合现有 app.asar 中的插件源码，得到以下结论：

1. **缺失值列为 unknown 后又被模板补全。** 通用提示词要求完整填写视角、共享规范，局部恢复缺少明确的交付分支；答案因此在前文保留 unknown，后文又以“完全居中的旧稿”作比较，并要求 M02 与 M01 同视角。档案并未给出这些值。此处是可见的指令冲突和输出错误，不能据此断言模型内部的唯一因果。
2. **恢复读取范围不清。** 入口原来要求恢复任务先找档案、确认和 MCP 状态，S4 又使用未限定的“恢复任务前”，课程资料还写首次加载即读。文字改稿被引向任务勘察、服务适配及课程重读。上一批必要档案读取成功；目录 read、猜 README 并非执行策略或文件权限故障。
3. **团队发现有明确的宿主指令来源。** 原生 runtime-context 的 `team:identity` 写有 `Use list_agents({}) to find your teammates and their names.`。安装包 `@deepseek-ai/dsh-experimental-tool-agent-team/lib/index.js` 的 `install()` 为确切 Agent scope 注册这段上下文和工具；`@deepseek-ai/dsh-tools/lib/index.js` 的 `restrict()` 明确仅限制全局工具，scope-local 注册仍可见。因此测试的全局 allowlist 没有隐藏团队工具，单调 guard 在执行时拒绝了它。当时尚未获得放行授权，不能把拒绝算成成功；后续获准的调整见文末。

保留真实 standard preset 和上述团队插件；没有卸载、替换或改写它们。Skill 仅明确本类局部文字任务不开展团队状态发现，不能宣称 Skill 文本能从宿主中移除工具或形成安全沙箱。

## 修复内容

- 入口按指定档案恢复，路径基于调用方工作目录；仅未终结的 MCP 任务进入服务恢复。课程方法仅在策划新方向需要时读取。
- 将分散在“任务头”的恢复限制移到恢复分支，明确资料充分后的读取终点；不猜文件、不将目录或二进制交给 UTF-8 read。
- 使用有证据位置的 K 字段、unknown 的 U 字段和新布局 N 条目作为单一来源，提示词与确认清单引用同一份记录。未知旧值保持 unknown，新位置写成新目标，不用“保持居中、上移、删除第三层”等词暗示旧稿事实。
- 完整草案允许显式的执行前缺口；实际提交仍必须补齐字段并确认。M01 冻结不等于 M02 的视角或共享规范已知／已批准，不把 M01 纳入再生成选项。
- 加严机械审计：本次固定的纯文字 recovery fixture 只允许读取指定档案与三个相关阶段资源；即使无关读取成功，也判失败。新增正反例覆盖 Windows 等价路径、成功读取无关 README、图片、另一份同名档案及无必要的 MCP 适配。

- 区分技能根与调用方目录，按宿主返回的完整技能根读取资源。测试会话不再暴露可切换目录的 `working_directory`；这是收窄测试能力，原 read 范围、团队工具拒绝和收费 guard 均保留。
- runner 按真实 `turn/end.reason` 与非空答案判断完成；上游过载、取消或空答案均为失败，不能再因出现 end 事件记成 completed。新增两项独立 Node 失败路径测试。
- 图片台账拆分业务角色、来源性质与绘图用途。合成夹具不改称真实商品，analysis_only 参考不分配绘图输入序号；说明、映射表和提示词使用同一范围。最后一轮两模型均保留合成来源，R01 不再一边说不上传、一边列为绘图图2。
- 失败行的机械统计也保留实际已返回的 image 块，不因其他步骤失败归零；补一项回归测试。这只修正计数，不放宽失败条件。

没有修改四类评测提示、夹具事实、模型路由、收费工具拒绝规则或降低语义量规。人工语义检查仍独立进行，不能由机械审计代替。

## 结论边界

本任务的“免费”指未调用收费图片服务；两种模型本身使用用户已有 codeproxy 推理配置，不宣称模型推理免计费。真实商品、实际出图／编辑、完整服务 plan／confirm／submit 链、取图和用户视觉验收仍需先确认方案并单独授权验证。

本轮不覆盖其他 profile／插件组合、桌面 GUI 点击预览、干净安装升级回滚、42×3 模拟全集或修改后包的 Codex 复验。旧 Codex 成功记录保留在其原有摘要范围内。一次主集通过也不是 Sonnet 后续必然稳定的统计保证。

已观察到但尚未根治的宿主可靠性风险包括：标准 profile 的团队发现指令与免费验证 guard 冲突、长 GUID 路径抄写，以及原生 read 的实际行数上限未在模型可见参数中充分表达。最后一轮未触发这些错误，不等于已修复上游实现；既有安装与配置没有被替换。

## 用户授权后的宿主发现门禁 v2

2026-10-23，用户明确允许根据上述宿主因素调整门禁。这是对先前“不放宽权限”边界的具体例外：测试会话内允许原生只读 `list_agents({})` 正常执行。会话级团队工具原本已可见，本次改变的是该只读调用的执行判定，没有安装插件或修改全局配置。

`dsh_free_guard.mjs` 只接受这个确切工具名及空参数对象，不接受目标会话、target 等扩展参数。guard 仍注册在测试 Agent 的 `agent.ctx`，原生工具从实际调用 Agent 解析本团队成员。创建队友、消息发送、打断／等待其他 Agent、共享任务操作、其他服务及收费图像入口仍拒绝；没有用“会话级工具”通配放行。原有路径、图片身份和确认／收费规则不变。

审计将宿主发现计为 `host_discovery_calls`，业务行为另计 `business_tool_calls`，同时保留总工具数。反例允许宿主发现，但仍必须零业务工具、零 Skill 调用、零 MCP；恢复中的目录／无关文件读取及旧稿推断仍失败。发现工具自身执行失败也仍判失败。未来完整主集的 `run.json` 标记 `gatePolicy.version=2`；旧结果不改写，不把这次例外用于追溯刷绿。

本地 **71 项 Python、9 项 Node** 检查通过，覆盖空参数放行、参数越界、其他团队工具继续拒绝、反例业务计数及收费门禁。另在本机原 Desktop Host 的全新独立测试会话，通过正常 `tools.execute` 的前置策略、guard、分发和结果流程实际执行 `list_agents({})`，返回成功。创建／消息／打断／等待及两家收费工具仅做 `guardReason` 预检，均保持拒绝，没有执行这些工具。

实际探针证据为 `.eval-runs/host-discovery-031c9a32-0801-4a44-9bbb-7b82f7dea4a4/result.json`：零模型请求、零收费出图，profile／锁文件／凭据摘要不变。此次只验证获准的门禁调整，**没有重跑双模型八场景主集，也不证明 Sonnet 旧稿推断已修复**；上文 Sol4/4、Sonnet3/4 的历史语义结论和任务进行中状态保留。
