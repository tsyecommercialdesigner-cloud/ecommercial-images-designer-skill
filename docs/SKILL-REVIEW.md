# 电商图片设计 Skill 审查记录

审查日期：2026-10-22。范围：用户两次功能需求、完整技能包、两个指定 MCP 的当前工具契约、确认及反馈回退。仅执行能力／资源只读调用和本地检查，没有创建真实商品方案、写入 MCP 确认或调用收费出图；没有 Git 操作。

## 结论

原版已覆盖主要业务阶段，但部分调用和批准粒度存在会阻断或误执行的缺口。本轮已修复下列问题，并补充 E29–E42。修复后的指令对用户全部需求均有处理路径；这仍是纯指令 Skill，其行为依赖宿主实际遵从，不能把条款和结构检查说成代码级强制门禁或真实视觉验收通过。

## 已发现并修复的问题

| 问题 | 原影响 | 修复与回归 |
|---|---|---|
| Nano 普通方案没有完整执行提示词导出 | 原说明要求“导出后核对”，却没有可执行的普通导出入口，容易把 panels 当 prompt，或卡在不存在的能力上。 | 明确 get 的范围，区分普通草案、suite、reference_replica 的真实导出路径；普通路径无法满足完整 prompt 交付时报告限制，经用户同意用另一指定服务；不臆造导出工具或绕确认。E29。 |
| 参考图业务角色与服务输入槽位不一致 | 通用模板曾假设产品图在前；复刻实际固定风格图在前。普通／suite 的 benchmarks 图并不传给模型。 | 按实际导出顺序、角色和 SHA 记录；分析参考与模型输入分开，仅结构参考不放进 style_only，禁止竞品进入 product_images。E30–E31。 |
| 服务范围与用户图数不匹配 | suite 必须主图、详情和 SKU 三类齐全，普通详情至少8屏；任意“整套”请求不能机械套用。 | 提前核对数量与类型；不能为通过模板增加用户没要的图、编造 SKU。能力不合时讨论另一指定服务。E32。 |
| 业务部分确认被扩成服务整版确认 | Nano confirm 没有 panel_ids，实际批准整个版本；提交子集不等于只批准子集。 | 分别记录 approval_scope 与 submission_scope，只在整个服务版本合法确认后调用 confirm；部分批准须构成独立执行方案或经同意采用逐图路径。E33。 |
| 改稿丢失未改图的定稿 | 普通 plan 从 brief 重建默认图，仅传本次 edits 会把其他自定义稿恢复为默认；suite 与复刻禁止普通 edits。 | 保留完整 brief、所有既定 edits，或完整 style/frames；比较全部差异后确认新版本。E34。 |
| 共享风格变更与局部修改混淆 | 改全套色调／字体系时，可能只重审一图并声称旧图仍属同一一致版本。 | 将共享 style 的所有关联图标为受影响；保留已接受旧产物，但明确其旧视觉组身份。底图及局部编辑能力先核对。E35。 |
| 复刻流程少了服务端复核 | 原来只在档案里记检查，没有调用 MCP 要求的 review_reference_replica。 | 实图观察后，以正确任务／版本／文件 SHA 保存六维具体证据，Agent 通过仍交用户判定。E36。 |
| GPT 参数约束不完整 | 比例字段、长详情尺寸、reverse 质量、异步／流式、mask 等可能传错或确认后静默修正。 | 补充字段转换与限制，在确认前解决不支持的参数；流式使用本服务同步入口，失败后不盲目切换重发。E37–E39。 |
| 停止、内容变更和反馈期间恢复不充分 | 停止后可能继续迭代；同路径图片换内容仍用旧批准；任务未知时借改稿重提；请求身份可能只在响应后保存。 | 明确终止条件，提交前保存身份及快照，核对输入内容，反馈可先计划而不重复收费；明确修订指令可承接原确认但不得扩大授权。E40–E42。 |

## 用户需求覆盖矩阵

| 用户需求 | 当前对应位置与判断 |
|---|---|
| 以指定飞书知识为基础 | source-methods 保存页面来源、实际读取范围、方法与案例边界；本轮沿用本对话已读内容，未声称重新读完全部附件。 |
| 策划选题 | S1 和 planning-and-prompts：受众、场景、购买疑虑、选题优先级及逐图任务。 |
| 卖点发掘 | 事实 ID→特征→用户收益→证据→主题，推论与事实分开。 |
| 文案与排版 | S2：主副标题、标签、脚注、布局、字体、色调、层级、证据锚点；整套共享规范。 |
| 提示词构造并提交 | S3 完整提示词结构；S4 按确认版提交；Nano 可导出入口与普通入口限制分别记录。 |
| 只使用指定两个 MCP Server | SKILL S4 与 mcp-adapters 的精确服务名称／工具前缀表，禁止其他生成工具替代。 |
| 取得生成产物 | 任务 ID／幂等身份、分段查询、真实文件／链接、部分成功、下载恢复和实际尺寸检查。 |
| 用户判断最终结果 | S5 先看实图再展示预览与文件，状态保持 pending，用户接受才记 accepted。 |
| 依据反馈回到正确阶段 | S0 事实／身份、S1 选题、S2 文案布局、S3 提示／编辑、S4 任务恢复；多个问题回最早受影响阶段。 |
| 可分步研讨 | 每轮给结论、待定项和下一步，用户可只取一个阶段，不强迫走完整套。 |
| 保留事实、参考来源、文案和排版 | design-record 的图片、事实、卖点、逐图方案、版本、确认、提交与产物台账。 |
| 方案确认后才绘图 | S3 门禁、确认证据及服务批准粒度；已批准方案改动按实际范围重新核对。 |
| 烘干箱参数仅是案例 | source-methods 明确同类新品也重新取得资料，不迁移任何案例参数、认证或售后。 |
| 首次生成需要用户图片 | 开始与资料边界，只有用户明确文生图素材才允许无图；普通概念请求不自动豁免。 |
| 首次与修改区分 | 修改需要可读底图及原约束，API 的 edit 端点名称不改变业务首次属性。 |
| 区分真实产品与竞品图 | 图片身份台账、用户证据、事实隔离；身份不明先澄清。 |
| 参考分风格、结构或两者 | 两条设计轴＋业务用途记录，并检查真实 MCP 槽位是否可表达该用途。 |
| 反馈后逐步落地 | 保留已接受产物和未变约束，新版本重走相关依赖；不全套盲重画、不无限重抽。 |

## MCP 核对证据与限度

- 当前实际工具声明：两个服务的提交、查询、等待、下载／取图；Nano 的 confirm、suite／reference 构造导出和 review。精确字段已同步至技能适配文档。
- 本轮实际调用：Nano `list_models`、GPT `get_model_guide`；均正常返回配置状态。Nano 返回 `upstream_verified=false`，不能据此声称供应商出图验证通过。
- 实际读取 Nano 资源：`nanobanana://templates/product-suite`、`nanobanana://templates/reference-replica`、`nanobanana://reference-replication`；据其工作流和 schema 核对三类整套、图像角色和复核流程。
- 为定位未在精简工具 schema 展开的约束，额外只读检查本机安装源码：Nano 的 design_models/design/design_tools/suite_tools/reference_tools/reference 与 GPT 的 contracts/api。没有修改服务源码或配置。安装源码仅用于本次审查，技能包不依赖这些本机路径。

没有执行实际 plan→confirm→收费 submit 链路、没有给合成资料写入真实用户确认，也没有运行独立模型／真实宿主多轮评测。E01–E42 是有断言的评测集及契约走查，不能报告为42次模型运行通过。原 Beads 后续验收任务继续跟踪这些未验证项。
